Porch includes two validating webhooks that validate PackageRevision and Repository resources. These webhooks require TLS certificates to function properly. 

**For production deployments**, you must use cert-manager or equivalent certificate management to ensure:
- Certificates are valid and properly rotated
- Certificate expiration doesn't cause validation outages
- Cluster security policies are met

By default, Porch generates self-signed certificates at deployment time, which is suitable for development/testing but not recommended for production.

## Porch Webhooks

Porch includes two validating webhooks running in the porch-controllers pod on port 9443:

1. **PackageRevision Webhook** (`porch.kpt.dev/v1alpha2`)
   - Validates: CREATE, UPDATE, DELETE operations on PackageRevision resources
   - Enforces: lifecycle transitions, immutable fields, render race prevention, upstream reference protection
   - Endpoint: `/validate-porch-kpt-dev-v1alpha2-packagerevision`

2. **Repository Webhook** (`config.porch.kpt.dev/v1alpha1`)
   - Validates: CREATE, UPDATE operations on Repository resources
   - Enforces: git repository conflict detection, directory nesting prevention
   - Endpoint: `/validate-repository`

Both webhooks share a single TLS certificate mounted at `/etc/webhook/certs` in the porch-controllers pod.

## Default Configuration

By default, Porch automatically generates self-signed TLS certificates for its webhooks at deployment time. The certificates are:

1. Generated by `scripts/webhook-utils.sh` during deployment
2. Stored in Secret: `porch-controllers-webhook-tls` in namespace `porch-system`
3. Mounted in the porch-controllers pod at `/etc/webhook/certs`
4. Referenced in ValidatingWebhookConfiguration resources via caBundle

**Limitations of self-signed certificates:**
- No manual rotation before expiration (webhook validation outage when expired)
- Not suitable for production use
- Best for development and testing environments only

**For production**: Use cert-manager (next section) for automatic certificate provisioning, renewal, and rotation.

### Cert-Manager Integration (Recommended for Production)

Cert-manager provides automatic certificate provisioning, renewal, and rotation. **This is the recommended approach for all production deployments.**

Cert-manager handles:
- Automatic certificate provisioning from your CA
- Renewal before expiration (zero downtime)
- Automatic caBundle patching into ValidatingWebhookConfiguration
- Certificate lifecycle management without manual intervention

#### Prerequisites

- [cert-manager](https://cert-manager.io/docs/installation/) v1.0+ installed in your cluster (v1.21.1 or later recommended)
- A configured ClusterIssuer or Issuer

#### Installation

Follow cert-manager's [installation guide](https://cert-manager.io/docs/installation/):

```bash
# Install cert-manager
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.21.1/cert-manager.yaml

# Wait for cert-manager to be ready
kubectl rollout status deployment -n cert-manager cert-manager
```

#### Configuration

1. **Create an Issuer** for certificate provisioning:

```yaml
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: porch-webhook-issuer
  namespace: porch-system
spec:
  selfSigned: {}
```

2. **Create a Certificate resource** (cert-manager will automatically manage the Secret):

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: porch-controllers-webhook-cert
  namespace: porch-system
spec:
  secretName: porch-controllers-webhook-tls
  commonName: porch-controllers.porch-system.svc
  dnsNames:
  - porch-controllers
  - porch-controllers.porch-system
  - porch-controllers.porch-system.svc
  - porch-controllers.porch-system.svc.cluster.local
  issuerRef:
    name: porch-webhook-issuer
    kind: Issuer
  duration: 2160h  # 90 days
  renewBefore: 360h  # 15 days before expiry
```

3. **Deploy to your cluster**:

```bash
kubectl apply -f issuer.yaml
kubectl apply -f certificate.yaml
```

Once created, cert-manager will:
- Automatically create and manage the Secret `porch-controllers-webhook-tls`
- Watch the Certificate and rotate before expiration
- Automatically patch the caBundle into both ValidatingWebhookConfiguration resources

No code changes required. The porch-controllers pod will automatically use the cert-manager-managed certificate.

## Configuration

Webhook certificates are mounted as a volume from the Secret:

```yaml
volumes:
- name: webhook-certs
  secret:
    secretName: porch-controllers-webhook-tls
    defaultMode: 0440  # Read-only
volumeMounts:
- name: webhook-certs
  mountPath: /etc/webhook/certs
  readOnly: true
```

The webhook server looks for certificates at:
- `/etc/webhook/certs/tls.crt` (certificate)
- `/etc/webhook/certs/tls.key` (private key)

## Certificate Rotation

### With cert-manager

Certificates are automatically renewed:
- cert-manager watches the Certificate resource
- Rotates certificates before expiration (renewBefore setting)
- Automatically updates the Secret
- Porch-controllers pod reloads certificates from updated Secret
- No manual intervention or downtime required

### With Self-Signed Certificates

Manual rotation is required before expiration:
1. Generate new certificates using `scripts/webhook-utils.sh`
2. Update the Secret
3. Redeploy webhook configurations
4. Porch-controllers pod restarts and loads new certificates

## Troubleshooting

### Check Webhook Registrations

```bash
# List webhook configurations
kubectl get validatingwebhookconfiguration

# Check PackageRevision webhook
kubectl describe validatingwebhookconfiguration \
  packagerevision-validating-webhook-configuration

# Check Repository webhook
kubectl describe validatingwebhookconfiguration \
  repository-validating-webhook-configuration
```

### Verify Certificate

```bash
# Check certificate exists
kubectl get secret -n porch-system porch-controllers-webhook-tls

# View certificate details
kubectl get secret -n porch-system porch-controllers-webhook-tls -o yaml | \
  grep tls.crt | awk '{print $2}' | base64 -d | \
  openssl x509 -text -noout

# Check certificate expiry
kubectl get secret -n porch-system porch-controllers-webhook-tls -o yaml | \
  grep tls.crt | awk '{print $2}' | base64 -d | \
  openssl x509 -noout -enddate
```

### Check Webhook Pod

```bash
# View pod status
kubectl get pods -n porch-system -l app=porch-controllers

# View webhook logs
kubectl logs -n porch-system -l app=porch-controllers | grep -i webhook

# Check certificate mount
kubectl describe pod -n porch-system -l app=porch-controllers | grep -A 5 webhook-certs
```

### Common Issues

**Webhook validation failing with certificate errors**
- Verify certificate is mounted: `kubectl describe pod ...`
- Check certificate hasn't expired
- Verify caBundle in webhook config matches certificate

**Webhook timeout errors**
- Check porch-controllers pod is running
- Review pod logs for webhook server errors
- Ensure cluster network is functioning

**cert-manager Certificate not ready**
- Check Certificate status: `kubectl describe certificate ...`
- Verify Issuer/ClusterIssuer is ready
- Review cert-manager logs: `kubectl logs -n cert-manager`

**caBundle mismatch after cert rotation**
- For cert-manager: cert-manager should auto-patch ValidatingWebhookConfiguration
- For self-signed: Verify caBundle matches the certificate Secret after rotation

## Production Deployment Checklist

Before deploying Porch to production:

- [ ] **Webhook TLS certificates configured** - Use cert-manager for automatic rotation
- [ ] **Certificate Issuer ready** - Issuer or ClusterIssuer deployed and verified
- [ ] **Certificate rotation tested** - Verify rotation works and doesn't cause outages
- [ ] **Webhook availability monitored** - Alert on webhook timeouts or failures
- [ ] **Certificate expiry monitored** - Alert before certificates expire (for manual rotation scenarios)
- [ ] **Pod replicas >= 2** - Multiple controller replicas for high availability
- [ ] **Webhook timeouts appropriate** - Default 30s suitable for most clusters
- [ ] **RBAC verified** - Service account has webhook management permissions

**Missing webhook TLS configuration is a production readiness blocker** - Webhooks must have valid TLS certificates to function. Without proper certificate management, webhook validation will fail when certificates expire, blocking all package operations.
